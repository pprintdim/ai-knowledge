# Структура оркестрації

## Ролі

**Claude (оркестратор)** — завжди сам:
- архітектурні рішення, все що потребує контексту розмови;
- git commit/push, фінальний огляд усіх diff-ів (жодних сліпих злиттів);
- SSH/деплой/CloudPanel/будь-що мережеве (Codex у sandbox `workspace-write` не має мережі — перевірено);
- security-чутливі зміни; дрібні швидкі правки (оверхед делегування більший за виграш);
- все, що треба перевірити в браузері/рантаймі;
- **будь-який SQL — описати і чекати підтвердження користувача ПЕРЕД виконанням** (виконавець неважливий — правило те саме).

**Codex CLI** (`npx --yes @openai/codex exec "промпт" --cd <шлях> -s workspace-write`) — окрема квота OpenAI:
- масові рефакторинги/перейменування по багатьох файлах;
- генерація boilerplate (OC controller/model/template тройки);
- великий пошук/аналіз по кодовій базі; рутинні тести/документація;
- рутинні БД-задачі (bulk update, міграції) — але SQL все одно через підтвердження;
- якщо впав у ліміт/помилку — НЕ чекати й не ретраїти: робити самому і повідомити.

**Субагенти Claude (Task/Agent)** — для перевірених повторюваних патернів (визначення в `~/.claude/agents/`):
- фонові, з нотифікацією про завершення; можна резюмити через SendMessage;
- **обовʼязково інструктувати писати результат інкрементально** — прогрес, не записаний на диск, гине при обриві (двічі втрачали переклад через session limit);
- агенти НЕ комітять і НЕ виконують SQL на проді — генерують файли, оркестратор перевіряє й застосовує;
- план на майбутнє: ізольована git-гілка для агентних робіт (не чіпають main/robochi гілки).

## Правила виконання (глобальні звички)

- **Деплой періодами**: користувач тестує на живому сервері — рсинкати+SQL після кожного логічного шматка, не батчити на кінець.
- Прод-деплой: `rsync -az --relative --files-from=...` (без `--relative` файли лягають плоско — наступали) → `chown -R <siteuser>` → `rm -f system/storage/cache/cache.*`.
- Ніколи `git add -A` без перегляду `git status` (1.5GB materials/ уже комітили випадково).
- zsh-пастка: `for x in $VAR` не сплітить — `${=VAR}`; цикли з curl глючать — окремі команди або PHP-скрипт.
- Довгі фонові задачі не кидати передчасно; штучний polling не робити (нотифікація приходить сама).

## Схема потоку задачі

```
Користувач → Оркестратор
	├─ дрібне/контекстне/мережеве → сам
	├─ механічне обʼємне → Codex CLI ──┐
	├─ повторюваний патерн → субагент ─┤→ файли/дифи
	└─ SQL → опис → підтвердження ─────┘
Оркестратор: перевірка дифів → деплой батчем → тест на проді → commit/push → handoff.md
```

## Handoff

У корені кожного проекту — `handoff.md` (gitignored): актуальний стан, пастки, доступи-шляхи. Оновлювати після етапів і ПЕРЕД стисненням контексту. Тільки актуальне, без хронології.

## Knowledge Layer (Obsidian vault = ця тека)

- Агенти групуються по доменах: `Agents/<домен>/` (зараз — `натяжки`); нові домени (wordpress, laravel…) — своя тека зі своїм набором.
- Перед задачею: [[WORKFLOW]] (repo → project memory → targeted knowledge search → код).
- Після задачі: harvesting за [[MEMORY-RULES]].

## Схема репозиторіїв (план, узгоджено 2026-08-07)

```
GitHub: ai-knowledge (цей vault) + project-a/b/c…
Mac:    ~/AI-Workspace/knowledge/  ← clone ai-knowledge
        ~/AI-Workspace/worktrees/  ← тимчасові shallow clone / git worktree під задачу
```

Не тримати 20 повних постійних копій: оркестратор бере потрібну репку → shallow clone/worktree → агент працює в ній (гілка `agent/<TASK>-<коротко>`) → commit/push → робоча тека видаляється. Схема приблизна, уточнюється в міру використання.
