# MEMORY-RULES — що зберігати, що ні

## Harvesting після задачі

Питання одне: **«Чи знадобиться це в ІНШОМУ проєкті?»**

- НІ → нічого не записувати. Vault ≠ dump логів.
- ТАК → короткий запис у відповідну нотатку `Knowledge/` (або нову, якщо тема нова).

Формат запису специфічного рішення:

```
## <Назва проблеми>
- Проблема: …
- Причина: …
- Рішення: … (приклад коду за можливості)
- Де застосовується / обмеження: …
- Джерело: <проєкт/коміт>
```

Проєктне (не reusable) — у `Projects/<repo>/MEMORY.md`, а не в Knowledge.
Конфлікт двох реалізацій → НЕ оголошувати одну «правильною», описати умови застосування кожної.

## Куди що

| Тип | Місце |
|---|---|
| Reusable технічне рішення | `Knowledge/<стек>/<тема>.md` |
| Повторюваний процес (чеклист) | `Patterns/` |
| Факт про конкретний проєкт | `Projects/<repo>/MEMORY.md` |
| Архітектурне рішення + «чому» | `Projects/<repo>/DECISIONS.md` |
| Стан задач | `Projects/<repo>/TASKS.md` |
| Застаріле | `Archive/` (не видаляти одразу) |

## ЗАБОРОНЕНО записувати у vault

- passwords, API keys/secrets, private keys, auth tokens
- вміст `.env`, DB-паролі, customer data, production-конфіги з секретами

Дозволено: назва інтеграції + ДЕ лежить конфігурація (шлях/файл), без значень.
Приклад: «Cloudflare purge-токен — просити в користувача» ✅; сам токен ❌.

## Гігієна

- Не дублювати: одне знання — одна нотатка, решта — `[[лінки]]`.
- INDEX.md кожної гілки Knowledge оновлювати при додаванні нотатки.
- Застарілі/спростовані записи — виправляти або в Archive, не залишати брехню.
