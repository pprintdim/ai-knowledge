# Етап 1: read-only CRM напряму з баз OpenCart

## Рішення

На першому етапі CRM читає актуальні дані **напряму з MySQL-баз OpenCart 3**.

Це рішення замінює вимогу з початкового ТЗ про обов'язковий OpenCart API-конектор. API-модулі, HMAC, callback та передавання змін назад у магазини зараз не реалізовуються.

## Обмеження першої версії

- Тільки читання даних.
- Жодних `INSERT`, `UPDATE`, `DELETE`, `ALTER`, імпорту або зміни статусів.
- У frontend немає активних кнопок збереження чи масового редагування.
- Для кожної OpenCart-бази створюється окремий MySQL-користувач лише з правом `SELECT`.
- CRM не використовує root або робочі DB-паролі магазинів.
- Паролі read-only підключень зберігаються зашифрованими в БД Laravel.
- Помилки підключення не повинні показувати пароль, DB username або серверний шлях.

## Laravel-архітектура

Frontend не повинен знати, звідки отримані дані. React звертається тільки до REST API Laravel.

У Laravel потрібні:

- `OpenCartConnection` — зашифровані параметри підключення, префікс таблиць і версія;
- `OpenCartReadGateway` — єдина read-only точка доступу;
- repositories для sites, products, categories, orders і customers;
- DTO/Resources, які відділяють структуру OpenCart від frontend API;
- перевірка існування таблиць і колонок для різних збірок OpenCart 3;
- pagination, filters, sorting і search на рівні SQL;
- короткий cache лише для довідників; замовлення й залишки читати актуально;
- журнал підключень і помилок без секретних даних.

Не дозволяти frontend передавати назву таблиці, SQL, довільну колонку або raw `order by`. Усі таблиці, поля, фільтри та сортування мають бути whitelist-овані в repository.

## Підготовка до майбутнього редагування

Редагування не додавати в read-only gateway. Для майбутнього запису створити окремий контракт `OpenCartWriteGateway`, який спочатку залишається без реалізації.

Перед увімкненням запису окремо потрібні:

- спеціальний DB-користувач із мінімальними write-правами або захищений OpenCart API-конектор;
- roles/permissions для кожної операції;
- preview змін і явне підтвердження;
- audit log до і після зміни;
- транзакції;
- optimistic locking за `date_modified`;
- резервна копія та сценарій відновлення;
- інтеграційні тести на копії БД.
